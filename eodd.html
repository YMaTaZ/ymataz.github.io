01

背景与问题

当一个系统替人做出判断，却无法说明判断从何而来，风险会同时落在三个方向。

LLM 已经进入医疗诊断、金融风控、法律推理等高风险场景。但"单体架构"意味着：一次决策由单个模型一口气生成，出错时既无法理解原因，也无从干预、难以追责。

更麻烦的是，现有的可解释性方法（LIME、SHAP 等）大多是对模型行为的事后近似——它们解释的是"模型可能怎么想"，而不是"这次究竟怎么判断的"。要让人真正信任并监督一个决策系统，需要的是可追溯、可干预的推理过程，而不是一张事后拼出的热力图。

三重风险：安全（错误无法拦截）、问责（责任无处落）、监管（合规无从审查）。

02

方法

七步 EODD 设计法，把一次决策拆成可分配、可编排、可审查的流程。

七步 EODD 设计法

01

决策情境定义

明确这次决策在什么场景、依据什么标准、对谁负责

02

决策分解

把一个复合判断拆成若干可独立检验的子问题

03

专用角色分配

为每个子问题指派一个专用 LLM 角色

04

编排规则

规定角色之间谁先谁后、如何交叉验证

05

决策综合

汇总裁决，并记录分歧所在

06

决策轨迹生成

输出完整、可审计的推理链路

07

人工审查集成

把最终判断权交回人，系统只负责解释与提示

四角色多智能体架构

Reasoner

推理者

基于证据给出初步判断，是决策的主要生产者。

Checker

检查者

校验推理链的每一步是否站得住，专挑漏洞。

Ethics Reviewer

伦理审查者

从公平、隐私、影响面等角度提出异议。

Explainer

解释者

把整条轨迹翻译成人能读懂的说明。

03

验证

三段式验证：先请专家看、再上规模评估、最后做用户实证。

Phase 1

专家启发式评估

由领域专家判断流程是否可行、解释是否成立。

N = 5
Phase 2

规模化可行性

用 LLM-as-Experts 在更大样本上检验稳定性。

N = 100
Phase 3

用户实证研究

对照实验，比较 EODD 与基线系统在各维度上的表现。

N = 16

05

复盘

三件我在这个项目里真正学到的事。

01

先把贡献边界说清楚

我在这个项目里是"研究协作 + 实证分析"，不是方法论首创者。把它写成"主导"，面试时一轮追问就会露馅——诚实标注身份，反而是最稳的表达。

02

可解释 ≠ 全都摊开

把整条推理链毫无筛选地展示，只会淹没使用者。真正起作用的是四角色分工 + 最后的人工审查那一步——它把"看懂"变成了"能干预"。

03

方法有边界

EODD 在需要审计的高风险场景里成立；但对低风险、快节奏的日常决策，七步流程很可能是过度设计。知道它"什么时候不该用"，和方法本身一样重要。
